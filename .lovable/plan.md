## Exactness rules followed

- Table, column, and type names copied verbatim, including quoted identifiers `"primary"` and `"json_value"`.
- Primary keys on `id`, except `master_transaction_additional` (`id_ad`) and `flyway_schema_history` (`installed_rank`, plain integer, not identity).
- All `id`/`id_ad` columns are `GENERATED BY DEFAULT AS IDENTITY`.
- All CHECK constraints kept as written (announcement target audience, merchant_service_requests status, referral_mapping status, services_catalog activation flow/type).
- All UNIQUE constraints kept (api_key_management service_code+environment, merchant_referral, merchant_service_application_data request_id, merchant_service_requests merchant_id+service_id, referral_mapping, referral_mapping_config, referral_wallet, services_catalog slug, master_transaction transid).
- Defaults kept: master_transaction `attempt_number` = 1, `is_orchestration_child` = false; flyway `installed_on` = now().
- No extra tables, columns, foreign keys, triggers, or renames.

## Access setup

Your backend connects to Postgres directly (JDBC/Flyway), so it is not affected by API-layer permissions. To keep the tables from being readable through the auto-generated REST API, the migration will:

- Enable row-level security on all 33 tables with no policies (locked to the API layer).
- Grant full table privileges to `service_role` only — no `anon`, no `authenticated`.

This is the safe default given these tables hold merchant PII, card metadata, API keys, and passwords. If any of these tables must be readable from the browser later, we add narrow policies then.
